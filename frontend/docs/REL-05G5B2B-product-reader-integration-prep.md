## Exactly one next implementation slice

**`REL_05G5B2B1_HEALTH_SELECTED_DAY_COMPOSITE_READER`**: a reversibly gated, read-only composite selected-day surface in Health, **including** the local/remote Health readiness split. These are one atomic product truth boundary: connecting the composite hook without splitting `AppContent`'s bootstrap gate would make offline/failure reads invisible; splitting startup alone would make legacy-empty UI appear complete before canonical is read. Do not connect Home, Search, Previous, metrics, Archive, export, or a canonical writer in this slice.

The gate is a repository-local, static build/config boolean defaulting **off**, following the simple `archiveShellConfig.ts` pattern; tests inject the enabled branch. No new remote flag service, account allowlist, localStorage override, or G5A readiness dependency. A dedicated, reviewed activation commit is required to switch on for users. With the gate off, legacy behavior stays byte-for-byte equivalent from the product's perspective. With it on in focused QA, Health explicitly identifies this as **selected-day-only, incomplete cross-app coverage**; no global “complete Workout history” claim. This is a reversible code-path rollout, not a writer cutover. Final copy/visual approval is a product decision before public activation.

Expected next-slice file scope, not changes made here: `AppContent.tsx` and its startup integration tests (readiness split/account scope), `useDaily.ts` and focused tests (expose local verified-read status without changing the legacy `Workout[]` cache type), `HealthView.tsx` plus focused integration tests (separate read-only section, status and action gates), `healthLocalRuntime.ts` plus focused tests (narrow persisted-row adapter), a new `features/health` composite loader/hook plus tests (two-source orchestration/fences), and a small static gate module. The canonical opener may need a small reusable read-only lifecycle helper near `workoutRuntimeAuthority.ts` or `localDatabase/repository.ts`; review its capability and generation fencing before adding that file, and keep any addition schema-neutral. `compositeWorkoutReadProjection.ts` and `WorkoutSessionRepository` remain frozen inputs unless a specific tested defect is found. No backend, IndexedDB version/index, V1 schema, push/pull, or sync-worker file belongs to this slice.

### Reader/loader contract

The product-facing model is **not** `Workout[]`:

```ts
type HealthSelectedDayReadModel = {
  scope: { accountId: string; namespaceKey: string; generationId: string; localDate: string; requestSequence: number };
  phase: 'loading' | 'settled'; // orchestration only; not a fabricated SourceRead success
  result: CompositeWorkoutReadResult | null; // only once both sources settle
  legacyEditableRows: readonly Workout[]; // existing legacy-only SWR/draft input; never composite
  canonicalReadOnlySessions: readonly Extract<CompositeWorkoutRecord, { source: 'canonical' }>[];
  visibleIds: readonly string[]; // G5B2A source-qualified readId, not raw row/session ID
};
```

When settled, derive `canonicalReadOnlySessions` and legacy read coverage from `projectCompositeWorkoutRead` without flattening canonical sessions. The existing legacy editor renders exactly once from `legacyEditableRows`; composite legacy records supply identity/completeness and, if needed, source-labelled persisted-row display, **not duplicate editor rows**. The selected-day projection filter is exact `localDate`; no historical row, unrelated date, or synthetic session is included. `result.status` remains `complete`, `partial_data`, or `error`; `loading` is a separate orchestration phase and must never be advertised as complete/empty. Source-qualified `readId` is the UI key and selection token. The projection's canonical-first stable fallback is not chronology; the display may use separate canonical/legacy groups, with no inferred interleaving timestamp.

**Legacy load:** `HealthRepository.readAll()` obtains `readAuthoritativeDatasets(accountId)`, which recovers pending import and checks `VERIFIED_IMPORT_COMPLETE`, dataset shape and counts. Add a narrow adapter over persisted `workout_logs` for the selected date, before `projectLocalHealthDaily` loses account/date and the range projection drops row ID. For each row carry exact persisted `id` (not `Workout.id` from a draft), `user_id` checked against authenticated `accountId`, `date`, `block_id`, safe nonnegative `sort_order`, cloned sets, and an explicit `current_catalog` versus `historical_fallback` display discriminant using the existing exercise-block map/fallback logic. A missing/invalid row identity or malformed row poisons the entire legacy source; do not silently filter it, synthesize a row ID, or call it empty. Keep the current local daily SWR key/value as a legacy `Workout[]`/daily projection; derive both normal legacy UI and composite adapter from a verified local snapshot where feasible, or explicitly coordinate two bounded reads and revalidation so a concurrent legacy save cannot produce a false complete/empty claim. Do not hydrate a clean draft from `[]` when the verified legacy source errored.

**Canonical load:** capture authenticated account, `HEALTH_ROUTINE_PROJECT_REF`, the shared durable device ID (`HEALTH_ROUTINE_DEVICE_ID_KEY`), `LOCAL_SCHEMA_VERSION`, and local DB metadata's `activeGenerationId`. Use `namespaceFingerprint`/`LocalDatabaseRepository.namespaceKey` from the actual opened namespace, never manufacture it from remote authority epoch or string concatenation. G5A's `openSharedActiveRepository` is private and opens a short-lived handle; `productionHealthRoutinePersistence` has a separate per-account session, not an exposed Workout product-reader lease. Use one account/project/device/generation-bound reader handle for a mounted scope (open once, close on scope/unmount, do not open per render), with the established `openLocalDatabase` capability pattern. If the initial namespace requires `initializeNamespace`, document and test that one-time metadata-only initialization; never treat malformed/stale metadata as success-empty. On active generation mismatch, close/reopen against metadata's active generation and recheck; never read an old generation as current. `WorkoutSessionRepository.queryWorkoutSessionsByLocalDate(date)` is acceptable for the first **gated, bounded** slice: it calls domain `listEntities`, which excludes tombstones and validates each V1. Construct `ActiveCanonicalWorkoutReadInput` from the actual envelope (`accountId`/namespace/generation, `entityId`, `localRevision ?? revision` only after equality/validity check, V1 record). Require `isDeleted=false`, `deletedAt=null`, account/owner match, actual namespace/generation match; a violated invariant is isolation/error, not a dropped row. Do not reimplement tombstone authority in G5B2A or the UI. Future ungated production scale needs a separately reviewed bounded/indexed query or account-generation snapshot cache; no schema change here.

**Scope/currentness:** each invocation captures `(authenticated account, namespaceKey, generationId, localDate, monotonically incremented requestSequence, component-mount epoch)`. Before every asynchronous continuation and just before publication, compare the captured tuple with current auth account, current device ID, locally active generation metadata, selected date, current mount epoch, and latest request sequence. Invalidate sequence synchronously on account/date/generation change, sign-out, remount, and manual refresh. Late A→B, A→B→A, date A→B, or G1→G2 result is **discarded without UI error flash** and never inserted into the new scope's cache. An actual account/namespace/generation mismatch in data raises `CompositeWorkoutReadIsolationError` and fails the entire composite; it is not a partial source failure. `HealthView key={authUser.id}` clears component state at account switch, but does not fence in-flight promises, SWR cache, or A→B→A. No auth ID alone is a sufficient token.

**Ordinary failure:** IndexedDB open/read failure, invalid V1, missing/duplicate persisted row identity, or source-specific malformed records become that source's `SourceRead.error`. G5B2A validates the whole source before composition. `success(empty)+success(empty)` alone gives `complete` empty; one error + one success gives `partial_data` with surviving source visibly incomplete; both errors give error/retry, not “no workouts”. An isolation failure suppresses **all** source records. Remote bootstrap pending is not a source read result. If verified legacy local data exists while Supabase bootstrap is pending/fails, that local data is readable; remote freshness/recovery status remains separate. If no verified legacy snapshot exists, legacy is error/unavailable until bootstrap succeeds and the local marker is verified; canonical local sessions may still show as `partial_data`. A bootstrap failure must not invent legacy success-empty. Retry revalidates only the affected account/scope. See [Supabase Auth changelog](https://supabase.com/changelog?tags=auth) for current auth platform changes; this slice makes no Supabase API/setting change.

### Startup split, SWR, and refresh

`AppContent.healthRuntimeReady` currently conflates `startupState.health.status === 'ready'` with local Health readability. The enabled path must start account-bound **local** verified legacy and canonical reads after auth scope is known, independently of the existing network bootstrap and independently of G5A `ready`. Keep the Supabase bootstrap retry/status for remote recovery. Once local Health source results settle, render the selected-day read-only canonical area even if remote bootstrap is pending/failed; allow legacy editor actions only when its verified legacy source is available and current. Preserve local-user behavior and the existing off-gate startup path. `useStaticData`/range/Previous may still fail without verified legacy data; their own errors must not be misrepresented as complete. Initial `loading` skeleton may cover both source reads, not indefinitely wait on network. The existing `HEALTH_LOCAL_BOOTSTRAP_COMPLETE_EVENT` and local writer invalidations trigger scoped rereads; a completed remote import rechecks the verified local snapshot and refreshes composite legacy status.

Keep `useDailyData`'s legacy `['local-health-daily', accountId, date]` cache as `LocalHealthDailyProjection`/`Workout[]`, and `useStaticData`'s `['local-health-static', accountId]` cache as legacy static data. Do not put `CompositeWorkoutReadResult` into either. Use a separate composite key containing source label, account, `namespaceKey`, active `generationId`, selected `localDate`, and a local invalidation epoch; the request sequence is a **publication fence**, not a persistent cache identity on every render. Do not share one key across accounts or generations. After legacy save/delete, revalidate legacy daily/static/range/Previous as today **and** the selected-day composite legacy side; after a canonical local change (future editor, adoption, sync, or another tab), invalidate the canonical side for that namespace/generation and recompose. No timer, keystroke, set-edit, or render-triggered full-domain scan. Read on mount/scope/date change, explicit retry, existing local bootstrap-complete event, and controlled focus/visibility (or cross-tab notification with a final scoped reread) for changes made by other tabs. On focus, reread local metadata before using a cached generation. Until a reliable cross-tab event exists, focus/visibility reread is required for the gated preview; background freshness remains a documented bounded risk.

Dirty legacy draft remains the only mutable workout buffer: legacy SWR refresh follows today's `isDirtyRef` hydration guard; canonical refresh updates its **separate** read-only cards regardless of dirty state. It never calls `replaceFromHydration`, `setLocalWorkouts`, `clearStoredDraft`, or legacy save. Discard means discard only the legacy transient draft, then rehydrate from verified legacy rows, not from canonical. Save/delete continue through `healthWorkoutPersistence` and cannot receive `CompositeWorkoutRecord` by type or callback. No canonical `createWorkoutSession`, `updateWorkoutSession`, `deleteWorkoutSession`, or `restoreWorkoutSession` product call. Canonical display never exposes the legacy delete button, drag handle, save/lock toggle, add-to-draft, or v7 writer action.

### Selected-day UX and consistency boundary

Canonical read-only cards show actual `WorkoutSessionV1` identity (`readId`/session ID), date, each entry's frozen exercise name/type/tags/cardio mode, ordered set type/ordinal/completion and type-correct weight/reps/assisted reps/duration/distance. Units come from V1 fields, not mutable legacy `exercise_blocks`; no fabricated performed time, session label, memo, or total chronology. Two V1 sessions on one date remain two cards; repeated exercises/sets remain distinct by their own IDs. Legacy editor rows retain current catalog or explicitly labelled historical fallback; a legacy date group is **not** a durable session. No content/name/date/sets dedupe between sources. Mixed day: a legacy-only editor section plus separate canonical session cards, with the source shown; canonical first only as a deterministic technical default pending product presentation sign-off.

The present empty state (`localWorkouts.length===0`) and summary/lock (`workouts.length>0`) are legacy-only. In enabled mode, a whole-day “no workouts” state is allowed only for settled `complete` with both sources empty **and** no dirty draft. A canonical-only day may show a legacy editor empty prompt, but it must be explicitly limited to the *legacy draft*, not a whole-day absence claim. `partial_data` must show the successful records plus an incomplete-coverage/retry state; no complete-history wording or total metrics. Both errors show error/retry. Canonical presence does not set `isWorkoutLocked` or route a save. The existing add-exercise duplicate check applies to the legacy draft only; whether to warn about a matching canonical exercise while permitting a separate legacy row is `PRODUCT_DECISION_REQUIRED`, and must be resolved before public activation. A preview may permit the legacy action only with source distinction; it must not silently dedupe or block by name.
