### Reader/loader contract

The product-facing model is **not** `Workout[]`:

```ts
type HealthSelectedDayReadModel = {
  scope: { accountId: string; namespaceKey: string; generationId: string; localDate: string; requestSequence: number };
  phase: 'loading' | 'settled'; // orchestration only; not a fabricated SourceRead success
  result: CompositeWorkoutReadResult | null; // only once both sources settle
  legacyEditableRows: readonly Workout[]; // existing legacy-only SWR/draft input; never composite
  canonicalReadOnlySessions: readonly Extract<CompositeWorkoutRecord, { source: 'canonical' }>[];
  visibleIds: readonly string[]; // G5B2A source-qualified readId, not raw row/session ID
};
```

When settled, derive `canonicalReadOnlySessions` and legacy read coverage from `projectCompositeWorkoutRead` without flattening canonical sessions. The existing legacy editor renders exactly once from `legacyEditableRows`; composite legacy records supply identity/completeness and, if needed, source-labelled persisted-row display, **not duplicate editor rows**. The selected-day projection filter is exact `localDate`; no historical row, unrelated date, or synthetic session is included. `result.status` remains `complete`, `partial_data`, or `error`; `loading` is a separate orchestration phase and must never be advertised as complete/empty. Source-qualified `readId` is the UI key and selection token. The projection's canonical-first stable fallback is not chronology; the display may use separate canonical/legacy groups, with no inferred interleaving timestamp.

**Legacy load:** For one selected-day load generation, call the verified `readAuthoritativeDatasets(accountId)` authority path exactly once (through `HealthRepository.readAll()` or a narrow shared loader). It recovers pending import and checks `VERIFIED_IMPORT_COMPLETE`, dataset shape and counts, yielding one `HealthRecoveryDatasets` snapshot. A conceptual `loadVerifiedSelectedDayLegacySnapshot(accountId, localDate)` returns one immutable paired result: an in-memory snapshot/load token, the existing `LocalHealthDailyProjection`/editor `Workout[]`, and persisted legacy rows for G5B2A, **both derived from that same verified snapshot**. Add the persisted-row adapter over `workout_logs` for the selected date before `projectLocalHealthDaily` loses account/date and the range projection drops row ID. For each row carry exact persisted `id` (not `Workout.id` from a draft), `user_id` checked against authenticated `accountId`, `date`, `block_id`, safe nonnegative `sort_order`, cloned sets, and an explicit `current_catalog` versus `historical_fallback` display discriminant using the existing exercise-block map/fallback logic. A missing/invalid row identity or malformed row poisons the entire legacy source; do not silently filter it, synthesize a row ID, or call it empty. The two derivatives publish together under the same current request/load token; settled `complete` or empty cannot pair editor rows read at T1 with composite persisted rows read at T3 across a T2 save. In particular, `readLocalHealthDaily()` followed by an independent `HealthRepository.readAll()` is **not** an allowed authority-read sequence for one composite publication. Preserve the existing `['local-health-daily', accountId, date]` cache/value contract as a legacy-only daily projection; a shared paired loader may feed that legacy projection and the separate composite orchestration without putting `CompositeWorkoutReadResult` in the daily cache. A failed verified snapshot makes **both** derivatives unavailable and the legacy source `error`; never hydrate a clean draft from invented `[]`. The load token is orchestration memory, not a new persisted revision or schema field.

**Canonical load:** capture authenticated account, `HEALTH_ROUTINE_PROJECT_REF`, the shared durable device ID (`HEALTH_ROUTINE_DEVICE_ID_KEY`), `LOCAL_SCHEMA_VERSION`, and local DB metadata's `activeGenerationId`. Use `namespaceFingerprint`/`LocalDatabaseRepository.namespaceKey` from the actual opened namespace, never manufacture it from remote authority epoch or string concatenation. G5A's `openSharedActiveRepository` is private and opens a short-lived handle; `productionHealthRoutinePersistence` has a separate per-account session, not an exposed Workout product-reader lease. Use one account/project/device/generation-bound reader handle for a mounted scope (open once, close on scope/unmount, do not open per render), with the established `openLocalDatabase` capability pattern. If the initial namespace requires `initializeNamespace`, document and test that one-time metadata-only initialization; never treat malformed/stale metadata as success-empty. On active generation mismatch, close/reopen against metadata's active generation and recheck; never read an old generation as current. `WorkoutSessionRepository.queryWorkoutSessionsByLocalDate(date)` is acceptable for the first **gated, bounded** slice: it calls domain `listEntities`, which excludes tombstones and validates each V1. Construct `ActiveCanonicalWorkoutReadInput` from the actual envelope (`accountId`/namespace/generation, `entityId`, `localRevision ?? revision` only after equality/validity check, V1 record). Require `isDeleted=false`, `deletedAt=null`, account/owner match, actual namespace/generation match; a violated invariant is isolation/error, not a dropped row. Do not reimplement tombstone authority in G5B2A or the UI. Future ungated production scale needs a separately reviewed bounded/indexed query or account-generation snapshot cache; no schema change here.

**Scope/currentness:** each invocation captures `(authenticated account, namespaceKey, generationId, localDate, monotonically incremented requestSequence, component-mount epoch)` plus the in-memory legacy snapshot/load token. Before every asynchronous continuation, cache write, and final paired publication, compare the captured tuple with current auth account, current device ID, locally active generation metadata, selected date, current mount epoch, and latest request sequence. Invalidate/supersede the same selected-day request sequence synchronously on account/date/generation change, sign-out, remount, manual retry, and a newer focus/visibility load. A committed legacy save or delete and a completed verified bootstrap/import invalidate the in-flight legacy load generation before either derivative can publish as current; the next load reads **one new** verified snapshot and derives both again. Do not merge pre- and post-write snapshots. A late pre-save, pre-delete, or pre-import result must not overwrite either the daily projection or composite cache with stale `complete`/empty. Late A→B, A→B→A, date A→B, or G1→G2 result is **discarded without UI error flash** and never inserted into the new scope's cache. An actual account/namespace/generation mismatch in data raises `CompositeWorkoutReadIsolationError` and fails the entire composite; it is not a partial source failure. `HealthView key={authUser.id}` clears component state at account switch, but does not fence in-flight promises, SWR cache, or A→B→A. No auth ID alone is a sufficient token.

**Ordinary failure:** IndexedDB open/read failure, invalid V1, missing/duplicate persisted row identity, or source-specific malformed records become that source's `SourceRead.error`. A failed verified legacy snapshot leaves both paired legacy derivatives unavailable; it cannot hydrate the editor from invented `[]`. G5B2A validates the whole source before composition. `success(empty)+success(empty)` alone gives `complete` empty; one error + one success gives `partial_data` with surviving source visibly incomplete; both errors give error/retry, not “no workouts”. An isolation failure suppresses **all** source records. Remote bootstrap pending is not a source read result. If verified legacy local data exists while Supabase bootstrap is pending/fails, that local data is readable; remote freshness/recovery status remains separate. If no verified legacy snapshot exists, legacy is error/unavailable until bootstrap succeeds and the local marker is verified; canonical local sessions may still show as `partial_data`. A bootstrap failure must not invent legacy success-empty. Retry revalidates only the affected account/scope. The canonical v7 read may run concurrently with the one verified legacy snapshot read; after both settle, recheck request/scope and compose with `projectCompositeWorkoutRead`. Legacy Health and canonical v7 are separate databases: this promises coherence between **legacy derivatives**, not a cross-database atomic transaction. See [Supabase Auth changelog](https://supabase.com/changelog?tags=auth) for current auth platform changes; this slice makes no Supabase API/setting change.

### Startup split, SWR, and refresh

`AppContent.healthRuntimeReady` currently conflates `startupState.health.status === 'ready'` with local Health readability. The enabled path must start account-bound **local** verified legacy and canonical reads after auth scope is known, independently of the existing network bootstrap and independently of G5A `ready`. Keep the Supabase bootstrap retry/status for remote recovery. Once local Health source results settle, render the selected-day read-only canonical area even if remote bootstrap is pending/failed; allow legacy editor actions only when its verified legacy source is available and current. Preserve local-user behavior and the existing off-gate startup path. `useStaticData`/range/Previous may still fail without verified legacy data; their own errors must not be misrepresented as complete. Initial `loading` skeleton may cover both source reads, not indefinitely wait on network. The existing `HEALTH_LOCAL_BOOTSTRAP_COMPLETE_EVENT` and local writer invalidations supersede any in-flight selected-day legacy snapshot/load token and trigger scoped rereads; a completed remote import rechecks one new verified local snapshot and refreshes both paired legacy representations.

Keep `useDailyData`'s legacy `['local-health-daily', accountId, date]` cache as `LocalHealthDailyProjection`/`Workout[]`, and `useStaticData`'s `['local-health-static', accountId]` cache as legacy static data. Do not put `CompositeWorkoutReadResult` into either. The separate composite SWR/cache identity is the **fixed scope key** `['health-selected-day-composite', accountId, namespaceKey, generationId, localDate]`. No local invalidation epoch, request sequence, mount epoch, refresh counter, timestamp, or random value belongs in a persistent key. `requestSequence` changes on each new load only as an in-flight/currentness publication fence; an old promise must not write even to the same fixed key after scoped revalidation starts. Use scoped `mutate(key)`/equivalent replacement semantics for legacy save/delete, verified bootstrap/import completion, manual retry, controlled focus/visibility refresh, and a canonical local change (future editor, adoption, sync, or another tab). A real account/namespace/generation/date change legitimately selects a new isolated key; old-scope data cannot publish into it, with ordinary SWR retention/cleanup rather than a correctness dependency on global cache deletion. Repeated invalidations of one unchanged scope reuse **one** cache entry, so refresh count cannot grow same-scope key cardinality; visited dates or genuinely different scopes may create entries, and no globally constant cache size is claimed. After legacy save/delete, preserve current daily/static/range/Previous invalidations **and** revalidate the fixed composite key, with the new paired legacy snapshot derivation above. A canonical change within the same generation revalidates its fixed key; an actual generation switch uses the new generation-qualified key. No timer, keystroke, set-edit, drag, or render-triggered full-domain scan. Read on mount/real scope/date change, explicit retry, existing local bootstrap-complete event, and controlled focus/visibility (or cross-tab notification with a final scoped reread) for changes made by other tabs. On focus, reread local metadata before using a cached generation. Until a reliable cross-tab event exists, focus/visibility reread is required for the gated preview; background freshness remains a documented bounded risk.

Dirty legacy draft remains the only mutable workout buffer: it may intentionally differ from the persisted paired legacy snapshot **before save**, and must not be treated as persisted composite evidence. Legacy SWR refresh follows today's `isDirtyRef` hydration guard; canonical refresh updates its **separate** read-only cards regardless of dirty state. It never calls `replaceFromHydration`, `setLocalWorkouts`, `clearStoredDraft`, or legacy save. Discard means discard only the legacy transient draft, then rehydrate from verified legacy rows, not from canonical. After a legacy save commits, invalidate the prior persisted selected-day load before publication and read one new verified snapshot for both saved/editor projection and composite legacy rows. Delete has the same invalidation rule. Save/delete continue through `healthWorkoutPersistence` and cannot receive `CompositeWorkoutRecord` by type or callback. No canonical `createWorkoutSession`, `updateWorkoutSession`, `deleteWorkoutSession`, or `restoreWorkoutSession` product call. Canonical display never exposes the legacy delete button, drag handle, save/lock toggle, add-to-draft, or v7 writer action.

### Selected-day UX and consistency boundary

Canonical read-only cards show actual `WorkoutSessionV1` identity (`readId`/session ID), date, each entry's frozen exercise name/type/tags/cardio mode, ordered set type/ordinal/completion and type-correct weight/reps/assisted reps/duration/distance. Units come from V1 fields, not mutable legacy `exercise_blocks`; no fabricated performed time, session label, memo, or total chronology. Two V1 sessions on one date remain two cards; repeated exercises/sets remain distinct by their own IDs. Legacy editor rows retain current catalog or explicitly labelled historical fallback; a legacy date group is **not** a durable session. No content/name/date/sets dedupe between sources. Mixed day: a legacy-only editor section plus separate canonical session cards, with the source shown; canonical first only as a deterministic technical default pending product presentation sign-off.

The present empty state (`localWorkouts.length===0`) and summary/lock (`workouts.length>0`) are legacy-only. In enabled mode, a whole-day “no workouts” state is allowed only for settled `complete` when **one valid verified legacy snapshot** yielded both an empty persisted-row representation and an empty legacy editor projection, the independent canonical source is valid and empty, there is no dirty draft, and the account/namespace/generation/date/request token is still current. A mismatched or stale pair cannot be published as `complete` empty, even if one derivative is empty. A canonical-only day may show a legacy editor empty prompt, but it must be explicitly limited to the *legacy draft*, not a whole-day absence claim. `partial_data` must show the successful records plus an incomplete-coverage/retry state; no complete-history wording or total metrics. Both errors show error/retry. Canonical presence does not set `isWorkoutLocked` or route a save. The existing add-exercise duplicate check applies to the legacy draft only; whether to warn about a matching canonical exercise while permitting a separate legacy row is `PRODUCT_DECISION_REQUIRED`, and must be resolved before public activation. A preview may permit the legacy action only with source distinction; it must not silently dedupe or block by name.
