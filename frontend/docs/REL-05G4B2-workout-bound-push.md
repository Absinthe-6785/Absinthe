# REL-05G4B2 — dormant bound Workout push and durable settlement

This is an explicit internal one-shot worker, not product activation. `runWorkoutPushIteration` has no AppContent, login, timer, online, visibility, or service-worker hook. G4B3 pull/full resync, G4C reset, G5 product cutover, and G6 ACTIVE/legacy writer fencing remain deferred.

## Eligible work and immutable wire request

`claimNextBoundWorkoutMutations` is separate from the generic REL-05D claim path. It selects only the oldest unsettled `health_workout_session` row per entity with a G4B1 `state: bound` binding, no `deliveryBlockCode`, an eligible pending/retry state or expired claim, and an acknowledged direct prerequisite. An unbound, quarantined, conflicted, or permanently failed predecessor blocks its successors. Generic workers continue to skip every row carrying `deliveryBinding`.

Each claimed row retains the existing v7 lease, attempt count, and last-attempt timestamp. The dormant driver claims one row immediately before processing it. A second tab may reclaim after expiry; settlement fences on worker owner plus attempt count and last-attempt timestamp, so a late prior attempt cannot write over the new attempt. There is no network I/O inside IndexedDB transactions.

The POST `/api/sync/v2/workouts/mutations` body uses only the bound outbox row. It sends the stored namespace/generation/device, `generationBindingId` as `bindingId`, authority epoch, lowercase wire UUID, mutation/idempotency identity, operation, frozen `remoteCasBaseRevision`, local revision, exact persisted payload/hash, and frozen request digest. `projectScope` is not sent. No current entity content is used to rebuild a request. Pre-send checks verify the active local generation and owner/device, lease attempt, binding/digest, payload hash, Workout payload identity, and local entity UUID. A fresh current Supabase session and synchronous account snapshot must match the row owner immediately before transport. No authority rediscovery or rebinding occurs during claim, send, retry, or settlement.

## Receipt and failure handling

HTTP 200 is insufficient: a success or exact replay must match domain, wire entity ID, mutation ID, idempotency key, operation, payload hash, authority epoch, and binding ID. It must contain a canonical remote mutation UUID, positive safe change sequence, valid committed timestamp, operation-appropriate content hash, and the CAS-derived server revision (`null` base → 1; N → N+1). Exact replay uses the original persisted server receipt. A lost response keeps the bound row in `retry_wait`; the next attempt sends the identical request. A push response never advances a pull checkpoint and no pull event fabricates an acknowledgement.

One IndexedDB transaction re-reads active generation, claimed row, exact attempt/binding, canonical entity, and lineage before settlement. Success stores `acknowledgedRevision = remote serverRevision`, `remoteMutationRef`, `serverCommittedAt`, local acknowledgement time/worker, and clears the lease/error. If the entity still represents that mutation, only its remote metadata and pending pointer advance. If a newer M2 is current, M1's receipt is stored on M1 alone: M2 content, local revision, pending mutation ID, and payload remain intact. Fresh G4B1 discovery can later bind unbound M2 against M1's acknowledged remote revision. An identical second settlement is idempotent; incompatible receipt evidence fails closed.

Network errors, timeouts, selected 5xx/429, authentication loss, and malformed/uncertain success use existing exponential `retry_wait` timing without changing the bound request. A switched account/device cannot send or settle another owner's row. `CAS_CONFLICT`, `ENTITY_ALREADY_EXISTS`, `NOT_FOUND`, and operation/state mismatch are durable conflicts; bounded server revision/hash/deletion/ref evidence is stored without applying remote content. `STALE_AUTHORITY_EPOCH`, `STALE_GENERATION_BINDING`, capability/foundation disabled, `AUTHORITY_EVIDENCE_MISSING`, digest mismatch, mutation/idempotency identity conflict, and invalid payload are permanent fail-closed states. Unknown deterministic rejections use `UNKNOWN_SERVER_REJECTION` rather than an unbounded retry. None of these paths changes authority epoch, binding, payload, request digest, or mutation identity.

No local DB version or schema changed (still v7); no backend contract changed. Diagnostics are event/code-only and never include tokens or Workout payloads.
