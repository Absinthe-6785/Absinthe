# REL-05G5A — account-scoped Workout authority bootstrap

G5A is the first product-lifecycle use of the dormant G4B1 control plane. An authenticated `AppContent` instance starts one bounded, non-blocking authority attempt for its account. The runtime reads or creates the existing durable Health/K323 device ID, opens the shared `absinthe-local-v2` v7 database, verifies its active shared generation, and calls G4B1 `discoverAndPersist`. That client reuses K323 generation registration, reads the Workout authority endpoint, registers the Workout generation only if the server requires it, and persists only authenticated `FOUNDATION_READY` / `OPEN` evidence with the server's trusted scope, epoch, binding, and server epoch. Persisted authority is not treated as a fresh authorization on the next run.

The app-shell controller has a monotonically increasing run identity. Account switch, logout/unmount, or superseding a run prevents its result from publishing status. The same identity is supplied to the authenticated G4B1 client as a live callback, so even rapid A→B→A cannot let the earlier A request settle merely because the account ID matches again. G4B1's existing IndexedDB discovery sequence and active-generation/account/device transaction fences remain authoritative. Ordinary same-account rerenders do not restart the effect, and concurrent starts within one controller run coalesce. No polling or automatic retry loop was added: network failure returns `retry_later` for a later lifecycle/event opportunity. Disabled capability and reset-fenced authority produce bounded internal status, not a Health startup failure or toast.

This slice **does not** bind Workout outbox mutations, push, pull, resync, begin/continue/recover reset, change the Health Workout reader/writer, dual-write the legacy Health database and v7, adopt `workout_logs`, add a legacy remote fallback, or alter G6. The existing Health startup gate and local product behavior remain independent of Workout authority discovery. The local database remains v7 without a store, index, or keyPath migration; backend code is unchanged.

Product cutover remains blocked on a reviewed historical-adoption policy, isolation of unbound pre-reset creates, and old/new client writer coexistence. Deployed G1 active-row provenance still requires the read-only precheck before Workout reset can be offered. G5A authority readiness is control-plane evidence only, not permission to claim Workout product convergence or G6 `ACTIVE` readiness.
