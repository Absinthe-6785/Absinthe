# K-89 — Real Usage & Large Vault Validation

**Branch:** `k89-real-usage-validation`  
**Status:** Validation complete  
**Scope:** Large vault performance, workflow friction, knowledge discovery, search UX, context IA, editor interactions  
**Constraint:** No new features — audit and measurement only

---

## Executive Summary

Absinthe is **production-ready for daily knowledge work up to ~500 notes** on a modern desktop browser. Beyond **1000 notes**, cold-start index rebuild and discovery feed generation become the dominant bottlenecks due to **superlinear related-candidate precomputation** in `KnowledgeIndexService.buildFromNotes()`.

The largest UX risks are **not performance** but **discoverability friction**:

1. Sidebar plain-text search does not filter the note list (K-87A gap, still open)
2. Knowledge Context has 11 tabs with overlapping metadata surfaces (K-87B)
3. Dual entry points (sidebar dashboard vs context panel) increase context switching

Recovery and export systems (K-88B/C) are validated separately; this audit focuses on day-to-day knowledge workflows.

## 1. Large Vault Simulation

### Methodology

- **Fixture:** `buildLargeVaultDataset()` in `realisticUsageFixture.ts` — representative mix of EJU, TOEFL, Japanese, Workout, and Reference notes with wiki links, folders, and tags
- **Harness:** `largeVaultBenchmark.ts` + `largeVaultUsageAudit.test.ts`
- **Measurement:** Median of 3 `performance.now()` samples per operation (`measureMs`)
- **Scales:** 250, 500, 1000, 3000 notes
- **Run:** `npm test -- largeVaultUsageAudit` (regression guard at 250/500; informational probes at 1000/3000)

### Observed metrics (local Vitest, Node environment)

| Notes | Vault (notes JSON) | Index build | Workspace search | Related notes | Discovery feed | Cosmos graph | Vault health | Plain sidebar filter* |
|------:|-------------------:|------------:|-----------------:|--------------:|---------------:|-------------:|-------------:|----------------------:|
| 250 | 72 KB | 82 ms | 3 ms | <1 ms | 25 ms | <1 ms | <1 ms | <1 ms |
| 500 | 144 KB | 328 ms | 1 ms | <1 ms | 46 ms | 1 ms | <1 ms | <1 ms |
| 1000 | 289 KB | **2,818 ms** | 6 ms | <1 ms | 229 ms | 3 ms | 2 ms | 2 ms |
| 3000 | 873 KB | **28,278 ms** | 13 ms | <1 ms | **1,543 ms** | 7 ms | 7 ms | 4 ms |

\* `plainTextFilterMs` simulates filtering via `noteSearchScore` — cheap when wired; **not connected** in `NoteView.visibleNotes` today.

Raw snapshot: `docs/k89-observed-metrics.json` (regenerated by audit test).

### Startup time (proxy)

Full vault reload triggers `KnowledgeIndexService.buildFromNotes()` in `useNotesStore.hydrateFromDB`. At scale:

| Notes | Cold index build | User-visible impact |
|------:|-----------------:|---------------------|
| 250 | ~80 ms | Imperceptible |
| 500 | ~330 ms | Brief delay on first load |
| 1000 | ~2.8 s | Noticeable spinner risk |
| 3000 | ~28 s | **Unacceptable** without incremental/index worker strategy |

K-83A incremental `updateNote()` mitigates **editing** paths; **full rebuild** on import/restore/new browser still hits this cost.

### Search latency

| Surface | 250–500 notes | 1000 notes | 3000 notes | Verdict |
|---------|--------------|------------|------------|---------|
| Workspace Search palette | <10 ms | <10 ms | <15 ms | **Good** |
| Sidebar plain-text list | N/A (unwired) | N/A | N/A | **Gap** |
| Find in Note | Per-note blocks | Same | Same | **Good** (K-87 fix holds) |
| Cosmos graph search | Dim/filter nodes | Same | Same | **Good** |

### Sidebar rendering

- Virtual list (`NoteSidebarVirtualList`) activates at **40+ notes** (K-86)
- Sort/filter at 3000 notes: **<5 ms** (simulated)
- **Bottleneck is not sidebar DOM** — it is index cold build and discovery when those panels open

### Knowledge context, related notes, backlinks

| Operation | Scaling | Notes |
|-----------|---------|-------|
| `groupRelatedNotes` (single note) | O(1) from precomputed index | <1 ms at all scales |
| Backlinks (index edges) | O(1) lookup | Good |
| Context panel tabs | Tab-gated (K-86) | Good when panel closed |
| Discovery feed (full vault) | Superlinear at 3000 | **1.5 s** — secondary bottleneck |

### Cosmos

- `buildGlobalGraphData` stays **O(N+E)** — 3–7 ms even at 3000 notes
- **Runtime Cosmos slowness** (documented K-83/K-86) comes from **force simulation + HUD analysis on mount**, not graph data build
- Full-graph render at 500+ nodes without focus note remains a **manual QA risk** (not measured in Node harness)

### Memory usage

`[MEM-AUDIT]` at 3000 notes during index build:

```text
relatedCandidates: 3,238,498
links: 3,749
```

Related-candidate precomputation in `buildFromNotes()` → `rebuildRelatedForNote()` for every note drives **O(n²) memory and CPU**. This is the root cause of index build regression at scale.

### Bottleneck summary

| Rank | Bottleneck | Severity at 1000+ | Location |
|------|------------|-------------------|----------|
| 1 | Full index rebuild (related precompute) | **Critical** | `KnowledgeIndexService.buildFromNotes` |
| 2 | Discovery feed full-vault scan | **High** at 3000 | `buildDiscoveryFeed` |
| 3 | Cosmos force simulation while open | **High** (manual) | `NoteGraphView` |
| 4 | Workspace search rebuild on keystroke | Low (debounced) | `buildWorkspaceSearch` |
| 5 | Sidebar list render | Low (virtualized) | `NoteSidebarVirtualList` |

## 2. Real Workflow Audit

Simulated workflows against current architecture (code review + K-83/K-86/K-87 prior art):

| Workflow | Steps (typical) | Friction | Click count |
|----------|----------------|----------|-------------|
| **Create note** | Sidebar + → type | Low | 1–2 |
| **Link notes** | `[[Title]]` in body OR Relations panel (More menu) | Medium — Relations buried | 3–5 for structured relations |
| **Search note** | Sidebar query → **no list filter** → open palette OR knowledge syntax | **High** — dual mental model | 2–4 extra |
| **Review related** | Open note → Links tab | Low | 2 |
| **Revisit stale note** | Discover tab OR Worth Revisiting in Links | Medium — Discover in More menu | 3–4 |
| **Archive** | Archive workspace | Low (separate surface) | 2+ |

### Redundant actions

- **Search:** Sidebar box + Workspace palette + Cosmos search — three surfaces, inconsistent semantics
- **Discovery:** Sidebar dashboard cards + Context Discover tab + Cosmos HUD — overlapping entry points
- **Tags:** Editable in Properties tab AND dedicated Tags tab in More

### Context switching

- Switching between **edit mode** and **Cosmos view** remounts graph (lazy, but still context break)
- **More menu** (6 items) hides high-value rediscovery paths (Discover, Timeline)

## 3. Knowledge Discovery Audit

| Surface | Rediscovery value | Weak point |
|---------|-------------------|------------|
| **Wiki links / backlinks** | High | Requires prior linking discipline |
| **Related Notes** | High | Precomputed; fast; good at all measured scales |
| **Worth Revisiting** | Medium | Heuristic; no `contentUpdatedAt` (K-87C) |
| **Insights** | Medium | Tab-gated; useful when opened |
| **Cosmos** | High spatial value | Heavy at 500+ nodes; lazy-loaded but still costly when open |
| **Discover feed** | Medium | Slow at 3000 notes; buried in More |
| **Isolated notes** | High for cleanup | Surfaces in discovery; good |

**Verdict:** A disciplined user **can** rediscover knowledge via Links + Related + search palette. Casual users may miss content because **sidebar search does not narrow the list** and **Discover is not prominent**.

## 4. Search UX Audit (K-87 revisit)

| Surface | Expected behavior | Actual | Status |
|---------|-------------------|--------|--------|
| **Find in Note** | Highlight raw text, no HTML corruption | Fixed K-87 | ✅ |
| **Workspace Search** | Ranked cross-vault results | Works; fast at scale | ✅ |
| **Sidebar search (plain)** | Filter/rank visible list | **Not wired** in `visibleNotes` | ❌ K-87A |
| **Sidebar search (knowledge syntax)** | `filterNotes` via workspace activation | Works | ✅ |
| **`nvSearchNoResults`** | Empty state when no matches | i18n exists, **unused** | ❌ |

**Conclusion:** Sidebar plain-text semantics remain **confusing** — the search box looks like a filter but only activates knowledge-syntax workspace mode or editor find-in-note scope.

## 5. Knowledge Context Audit

**Primary tabs:** Outline | Links | Cosmos | Insights | Properties  
**More (6):** Actions | Discover | Timeline | Tags | Relations | Stats

| Concern | Finding |
|---------|---------|
| **Tab usage (heuristic)** | Outline + Links highest; Properties medium; Cosmos/Insights medium when exploring |
| **Discoverability** | Relations, Discover, Timeline, Stats require More menu — low discoverability |
| **Redundancy** | Tags ⊂ Properties; Links ∩ Relations partial overlap |
| **Cognitive load** | 11 tabs exceeds Miller-style comfort; More menu is a junk drawer |
| **K-86 mitigation** | Tab gating prevents hidden-tab compute cost — **good engineering** |

**K-87 recommendation still stands:** Option B (Metadata group) long-term; Option A (promote Relations) for minimal change.

## 9. Guarantees & Non-Goals

### Validated guarantees (≤500 notes)

- Workspace search <15 ms
- Related notes / backlinks instant (precomputed index)
- Sidebar virtualized; sort/filter cheap
- Cosmos **graph data** build <10 ms
- Editor selection/delete model coherent (K-87D)
- Find-in-note highlight safe (K-87)

### Not validated in this sprint (manual QA still required)

- Cosmos **render** at 500+ nodes with force sim
- Mobile note editing + context overlay
- 500–1000 block single-note editing
- Memory pressure / OOM under long sessions (see K-83A)

### Explicit non-goals (per K-89 constraints)

- No new features shipped
- No product redesign
- No new workspaces
- No AI functionality
