### Legacy and canonical storage are not interchangeable

The legacy DB is `absinthe.health.local` v1. `workout_logs` has `storageKey = accountId:workout_logs:rowId`, an `accountId` index, and rows written as `{id,user_id,date,block_id,sets,sort_order}`. The writer requires a verified import state, treats `(date, block_id)` as a unique logical key, hashes the logical row set as `local_version` for CAS, replaces same-key rows transactionally, and physically deletes rows. It captures mutable `exercise_blocks` separately. A view-only `__session__` separator is filtered before persistence. There is no durable human-session boundary or historical exercise snapshot. See `healthLocalRepository.ts`, `healthLocalRuntime.ts`, `healthWorkoutPersistence.ts`, and `REL-05G3-workout-legacy-adoption.md`.

The canonical DB is `absinthe-local-v2` v7, separately opened with an account/project/device/generation namespace. `WorkoutSessionV1` is *exactly* `{version:1,id,localDate,entries}`. Each entry has a UUIDv4, frozen `{id,name,type,tags,cardioMode}` exercise snapshot and ordered sets with UUIDv4 and one-based ordinal. Set variants are strength/bodyweight/cardio; canonical numeric values are bounded decimal strings or safe integers. The `LocalEntityEnvelope` owns local revision, tombstone (`isDeleted`/`deletedAt`), remote state/revision, provenance and pending mutation identity. `WorkoutSessionRepository.create/update/delete/restoreWorkoutSession` writes the entity and an explicitly **unbound** outbox record in one v7 transaction; update/delete/restore require expected local revision. `listWorkoutSessions()` excludes tombstones through `listEntities` and `queryWorkoutSessionsByLocalDate()` currently filters that list in memory. It does not provide a product mode, date index, or UI projection. See `workoutSessionV1.ts`, `workoutSessionRepository.ts`, `localDatabase/types.ts`, `localDatabase/repository.ts`.

Important negative facts: V1 has **no** `performedAt`, `timeZone`, memo, session label, or session sort field; exact-key validation rejects them. The current UI `Workout`/`WorkoutSet` types have **no** stable session/entry/set UUIDs. A legacy row ID identifies an exercise/date row, not a canonical session. `HealthView` offers editing after local save and a delete-per-exercise-row action; no canonical restore UI is exposed. These are explicit cutover design gaps, not fields to fabricate. `workoutMemo` is a date/account localStorage note; it is not part of saved Workout history. Routine presets, blocks, InBody, and day notes remain separate domains.

## Historical coexistence decision

| Strategy | Fidelity and continuity | Duplicates/consumers/future cost | Decision |
| --- | --- | --- | --- |
| A. Read-only legacy history, v7 for new records | Honest about missing session/snapshot evidence; preserves visibility and Previous behavior | Requires composite Today/history/Analytics/Search projections and explicit source IDs; later archive retirement is deliberate | **Recommend**, subject to product approval |
| B. User-reviewed adoption | Can produce a reviewed canonical record with provenance | Substantial review UX, session/snapshot confirmation, duplicate suppression and rollback semantics; outside first G5B slice | Future explicit workflow only |
| C. Hide legacy from primary Workout UI | Simplest v7-only reader | Existing history/Previous/analytics appears lost; poor rollback and support cost | Reject for current cutover |

G3 established **zero automatically adoptable historical rows**. Never group `workout_logs` by date into invented sessions, mint historical session IDs, or use today's exercise catalog as a historical snapshot. Legacy records remain separate, read-only compatibility records until explicit, reviewed adoption with durable source-row mapping/provenance and confirmation. This recommendation is a `PRODUCT_DECISION_REQUIRED`, not a policy already encoded in the repository.

Proposed deterministic boundary: durable record **source provenance**, not a deployment timestamp or date. V7 records have a canonical session UUID and `health_workout_session` envelope under the scoped namespace. Legacy records keep the account + source DB/source type + original row ID and `local_version`. The two are distinct even on the same date with identical exercises/sets. Only an explicit reviewed adoption link can suppress a legacy item; date/name/value dedupe is forbidden. An old offline client can create a legacy row after new-client deployment, so "created after cutover" is not sufficient. A per-account rollout marker is needed for authorization/UX, but is not evidence that an arbitrary row is canonical.

Composite reader contract after a future gated cutover: account-scope both sources, exclude v7 tombstones, label legacy cards **Historical workout — read only**, order by localDate descending and within a date by source then canonical session ID/legacy row order+ID (stable tie-breakers). Preserve all same-day v7 sessions as separate identities; do not collapse them to the current date singleton. On Today: no record → new v7 draft; legacy-only → read-only legacy plus a separately labelled new v7 action, never edit the legacy row into V7; v7-only → select one session by ID for edit/delete; both → distinct cards and explicit choice; dirty draft → never hydrate over it, even after source refresh. If product wants editing of old rows, that is a later explicit user-reviewed adoption decision, not a hidden save target.

Previous Workout needs a composite source-aware lookup with deterministic precedence by actual prior date and stable source/session ID, not the existing one-session-per-date helper alone. Health month/calendar and Health analytics need a unified projection whose **session count** counts v7 sessions but treats legacy date-grouped rows as legacy days or explicitly labelled legacy groups; the current `monthlySessionCount` increments per range row and cannot be reused as a session metric. Home needs the current-day projection. Global Search currently searches only the selected day's legacy `Workout[]`; its result ID `workout-${rowId}` needs source and v7 session/entry identity to avoid collision. The active Archive tab has no live Workout reader; if Workout analytics are later surfaced there, they must use the same projection. CSV is currently unavailable for `LOCAL_FIRST`; any future export must include V7 via an account-scoped local projection, not silently export only `/api/workouts/range`.

## Proposed adapter and writer contract (not implemented)

Use a pure, strict `WorkoutSessionV1` ↔ **new typed editor model** adapter near `frontend/src/components/views/features/health/`, not an implicit conversion of bare `Workout[]`. Editor state must carry session ID, expected local revision, entry ID, set ID, localDate, frozen exercise snapshot, and ordered set data. A display projection may expose legacy `Workout` fields, but its source ID must stay attached and read-only. Hydrating an existing v7 session never generates IDs; adding a session/entry/set generates UUIDv4 exactly once in draft state; reorder/delete preserves every surviving ID. One canonical session can contain multiple entries; multiple sessions on a date remain separate. A `__session__` UI separator must **not** be silently dropped: either represent multiple explicit session drafts or reject that draft as unrepresentable until UI design is approved. Same-block duplicate entries must not be collapsed by legacy `(date,block_id)` assumptions.

Freeze the current exercise block's `id/name/type/tags/cardio_mode` into the V1 snapshot at *new* session creation (including routine-derived setup); later catalog renames must not rewrite it. `localDate` is the selected semantic date; never derive identity from UTC. `performedAt` and `timeZone` are absent from V1 and from the current saved legacy row: do not claim preservation or extend the frozen V1 in G5B. Keep date-scoped memo separate unless product decides it belongs to a session, in which case a separately reviewed model change is required. Decimal conversion must use V1's `normalizeWeightInput`, `normalizeKilometersToMeters`, `normalizeCardioDurationInput`, `normalizeRepetitionInput` and `normalizeAssistedRepetitionsInput`; Health's floating-point `healthWeight.ts` normalizer is not an exact substitute. Preserve the input unit/source value. Derive pace for display only.

Future new-record writer is **v7 only**: account-scoped `WorkoutSessionRepository.create/update/deleteWorkoutSession`, never a parallel `HealthRepository.saveWorkouts` or remote legacy POST. Save succeeds only after the v7 entity+outbox transaction completes. The outbox stays `{version:1,state:'unbound'}`; no bind, push, pull, resync or reset during G5B. Delete creates a tombstone, retained for later convergence, not a legacy hard delete. Restore API exists but is `NOT_CURRENTLY_EXPOSED` in the Health UI. Local CAS rejects stale `expectedLocalRevision`; tab B must preserve its draft and show conflict after tab A advances revision, never last-write-win. Re-read the active namespace/generation and fence account/date/run before committing or publishing a result. One shared v7 DB does not imply that an authority controller's `workout_authority` capability is a reviewed product-writer lifecycle; provide an explicit scoped product opener in the implementation, not a cross-account singleton. Local save must not call or wait for G5A discovery, and `ready` is not a save precondition.

Health's current lock is `workouts.length > 0` or successful local save, not remote ACK; future v7 lock should follow durable local commit. Replace `mutateDaily`/`mutateMonthWorkoutRows` for canonical records with account/date-scoped canonical projection invalidation. Keep legacy invalidation only for legacy history. Legacy Supabase bootstrap may continue to refresh **legacy** read-only history but must never write, overwrite, or synthesize V7. Current `AppContent` blocks Health until legacy bootstrap is ready and shows startup failure on failure; this must be split so an offline canonical session can hydrate while legacy history is separately loading/failing. Do not release the existing Health account-isolation boundary until the V7 repository and all async reads/writes are keyed by account and generation.

## Why a product writer cutover is not yet safe

1. **`G5B_UNBOUND_PRE_RESET_CREATE_BLOCKER` — code/architecture.** G2 creates an unbound first-create with no remote baseline. G4B1 can later bind it under fresh authority with `remoteCasBaseRevision=null`; the frozen outbox does not prove the creation-era epoch. A reset between offline creation and binding could make old intent look like a new-epoch create. G5C (or a separately reviewed pre-cutover isolation slice) must add durable creation-era evidence and quarantine/resolve stale intent before binding. Merely leaving it unbound today is safe only while no binder is activated; it is not proof of future convergence.
2. **`G5B_ROLLBACK_VISIBILITY_BLOCKER` — product/rollout.** An old frontend reads only legacy Health. A V7-only save followed by deployment rollback hides the new record from the product although its bytes survive. No dual-write escape hatch is safe across the two DBs. Until a rollback-compatible reader or an approved forward-only rollout strategy exists, V7 product writes are limited to disposable/staged test accounts with explicit recovery procedure; do not enable for general users.
3. **`G5B_OLD_NEW_WRITER_COEXISTENCE_BLOCKER` — rollout.** G6 has not fenced old clients. They can still write legacy rows, including offline rows arriving later. Composite reading can show both honestly but cannot assert cross-version convergence or automatic dedupe. Real-user rollout requires a reviewed coexistence restriction and G6-era fencing plan.
4. **`G5B_UI_IDENTITY_GAP` — code.** `Workout[]`, `WorkoutSet`, draft storage, Today hydration, legacy date grouping, and view-only session separators cannot round-trip V7 multiple-session/entry/set identities as-is. Strict adapter plus UI state work is required before wiring a writer.
5. **`G5B_CANONICAL_FIELD_GAP` — product decision.** V1 intentionally lacks per-session memo, `performedAt`, `timeZone`, and session labels. The current memo is separate. If these must be durable session fields, a separate reviewed contract decision is needed; G5B cannot add them invisibly.
6. **`G5B_ANALYTICS_PROJECTION_BLOCKER` — code.** Health's range metrics and Previous, Home, Search are legacy-shaped. Enabling V7 writes before composite read projections would make new data absent or miscounted.
7. **Reset-fenced local edit policy — architecture/product.** G5A status must not gate local-first persistence. Once a V7 writer is introduced, locally durable edits during `reset_fenced` can continue only with explicit unbound/quarantine semantics and a bounded "saved here, not yet synchronized" status; never rebind old-epoch intent automatically. The exact user warning/resolution is a product decision. Until designed, keep the writer dormant.

G5A's malformed device ID P3 is not a G5B save dependency: the local writer must not wait for the authority controller. Track `REL05G5A-001` separately. G4C's active G1-row provenance preflight remains a distinct production reset prerequisite; no reset is activated here.

## Rollout order and first implementation slice

Revised order: (1) **dormant pure typed UI/V1 adapter and tests** (the one immediate next implementation slice); (2) read-only account-scoped composite Today/history/Previous/Health metrics/Home/Search projection plus separate Health bootstrap readiness, still no product writer; (3) durable creation-era/reset quarantine and rollback/coexistence policy with G5C data-plane review, then a separately gated test-account V7-only writer; (4) physical offline/restart/same-device tests, then cross-device/push/pull/reset tests after G5C and G6 gates. Do not infer that a numbered G5B-before-G5C product activation is safe merely because G5B code lands first.

Immediate slice planned files: a new pure `frontend/src/components/views/features/health/workoutSessionEditorAdapter.ts` and `workoutSessionEditorAdapter.test.ts`; optionally a type-only companion in that directory. It must remain uncalled by `AppContent`/`HealthView` and perform no DB/network access. Tests: new UUID allocation once, hydrate/edit/reorder/delete identity stability, multiple entries/sessions with same date, exact snapshot freeze, decimal/cardio/bodyweight round trips, strict rejection of unrepresentable separator or memo, and no remote data-plane import/call. Do **not** create a production capability, mode flag, backend/schema change, or product cutover in that slice. The proposed adapter must document any V1-unrepresentable field rather than discard it.

Later product acceptance matrix: create/edit/delete and offline restart; date switch/dirty draft; account A→B→A including stale async result; two tabs at revision 3 where only first CAS commit succeeds; same-day multiple V7 sessions and legacy+V7; previous/analytics/Search/Home projection; draft parse/DB/quota/namespace/generation/CAS failures; tombstone hidden but durable; no bind/discoverAndBind/push/pull/full-resync/reset calls; old-client/rollback visibility drill. G5B can physically validate same-device offline durable save/restart only when a staged writer exists. Cross-device convergence, response-loss replay, remote conflict and reset convergence require G5C/G6.

| Failure | Required disposition |
| --- | --- |
| V7 open blocked/fails, quota, transaction abort, invalid canonical payload | `FAIL_SAVE_PRESERVE_DRAFT`; no success toast, no legacy fallback write |
| Namespace/account mismatch or stale generation | `FAIL_CLOSED` / `RECOVERY_REQUIRED`; retain scoped draft, never settle under another account |
| Stale local CAS | `FAIL_SAVE_PRESERVE_DRAFT`; show conflict and reload/review option, no overwrite |
| Draft parse failure | `RECOVERY_REQUIRED` or bounded explicit discard; do not treat malformed draft as saved canonical data |
| Legacy history read/bootstrap failure | `SHOW_READ_ONLY_HISTORY` only if verified local history remains; canonical Today must still hydrate independently, otherwise show history unavailable |
| Transient V7 read failure | `RETRY_LOCAL`; no fabricated empty-success state |

Decisions for product owner before live writer: approve read-only legacy-history UX and same-day mixed-card semantics; decide whether memo/session labels/time metadata are session-owned; approve reset-fenced local status and old/new-client plus rollback policy. These are **not** decided by existing code. Every source-authority boundary above is a code fact; the single-writer/no-fabrication/no-auto-rebase requirements are architecture constraints; the UX/rollout choices are product decisions.
