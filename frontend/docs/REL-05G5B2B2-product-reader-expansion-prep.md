## Previous and metric semantics that must not be lost

`previousWorkoutSession.previousWorkoutRange` covers one year before the reference date, ending yesterday; `listPreviousWorkoutSessions` filters empty-set rows, groups by date, sorts dates descending and rows by `sortOrder`, `rowId`, then original index. `defaultPreviousWorkoutDate` chooses newest same weekday or newest date; explicit `selectedPreviousDate` is preserved while still present. That is a **legacy date browser**, despite its type name. A new composite history model should have one date bucket with zero/one legacy group (row IDs retained) and zero/many separately identified canonical sessions. Date selection is safe; automatically selecting a *session* within a mixed/multi-session bucket is `PRODUCT_DECISION_REQUIRED`. Without V1 `performedAt`, inter-source or same-day chronology cannot be claimed; canonical UUID technical order is only a stable tie-break. Existing legacy set suggestion and PR lookup is separately keyed by `block_id`, not the chosen Previous date; do not silently merge those contracts. Same exercise ID can support an approved analytical comparison, not adoption or record equivalence. A legacy block may be mutable/missing, while canonical exercise is frozen and its `id` may be null.

`RangeWorkoutRow` has date/block/name/sets but not a durable session ID (and its range projection drops the legacy row ID). `monthlySessionCount` is row count; `countWeeklySessions` counts distinct dates; recent “sessions” groups exercise names by date; streak counts consecutive active dates anchored on selected date; weekly chart sets 0/1 per date; exercise history counts rows per name; PR highlights compare name-keyed completed strength kg. For a **complete** composite range, `activeDays = union(legacy row dates, canonical session dates)` is a truthful calendar/streak input without cross-source record dedupe. Canonical session count and legacy row/date-group counts must remain separate. A mixed “session total,” previous auto-selected session, name-only PR, volume or cardio conversion, and the copy for incomplete downstream data are `PRODUCT_DECISION_REQUIRED`; do not reuse `monthlySessionCount` under its current label. Lists may display surviving records with `partial_data`, but total/streak/count/calendar **absence** must be suppressed or conspicuously incomplete when either source fails. A partial active-day set can be shown only as known-present evidence, never as a complete month. Both sources success and empty is the only truthful complete empty; both fail is error; account/namespace/generation mismatch fails closed, not partial.

| Future range-derived value | Policy on `partial_data` | Complete-data meaning, if approved |
| --- | --- | --- |
| Source-qualified history list / known-present calendar dates | **SAFE_UNDER_PARTIAL_DATA** only with visible incomplete-source state; unknown dates are not “no workout.” | Preserve each record/session; date union for marks. |
| Weekly active-day count, recent-date list, streak, weekly chart, exercise-history count, legacy row/date-group count, canonical session count | **MUST_SUPPRESS_OR_LABEL_INCOMPLETE**; a surviving-source value is only a lower bound and cannot be labelled a complete total or streak. | Distinct-date union for active days, canonical IDs for canonical sessions, persisted row IDs for legacy rows. |
| Mixed-source `monthlySessionCount`/“sessions,” cross-source PR or volume/cardio total without approved units/exercise matching | **MUST_NOT_COMPUTE** under partial data or while the product definition is unresolved. | Separate typed metrics/approved conversion; never rows = sessions. |

V1 remains exactly `{ version: 1, id, localDate, entries }`; each entity is one durable session and any number may share a date. No `performedAt`, time zone, memo, session label or session sort exists. Its ordered entry/set IDs and frozen exercise snapshot must survive projection. The legacy date group has no durable human-session boundary; `__session__`, date, array index, hash and similarity of exercises/sets cannot mint one. The canonical payload's `localDate` is the range boundary, not a timestamp. No content similarity dedupe or guessed adoption relation is permitted.

## Recommended read architecture and bounded read budget

**Needed before a composite Previous/calendar/range UI:** a dormant, readonly account/generation-scoped Workout range snapshot boundary. Keep B1 `WorkoutSelectedDayReader` and its date-specific hook intact. Reuse its established-device-ID check, namespace/generation open, `workout_reader` capability, active-generation verification and close semantics in a small read-only helper or separate range reader; do not generalize the B1 hook into a cross-surface cache. `WorkoutSessionRepository.listWorkoutSessions()` already validates V1/UUID agreement and calls `listEntities({domain: WORKOUT_SESSION_DOMAIN})` with default tombstone exclusion; `queryWorkoutSessionsByLocalDate` does a **whole-domain** list then filters. The range reader should perform **one** active canonical list for a scope, validate account/namespace/generation/envelope before projection, then filter/project many dates in memory. Do not loop over dates and call `queryWorkoutSessionsByLocalDate`: N dates would cause N full-domain scans. `LOCAL_DATABASE_VERSION=7`, `LOCAL_SCHEMA_VERSION=1`; no new store/index/schema in this slice. If measured cardinality makes a full-domain scan too slow, separately gate an indexed-query/schema proposal; do not smuggle it into this prep.

Likewise one `createLocalHealthRepository(accountId).readAll()` is the verified `HealthRecoveryDatasets` authority snapshot. Current `readLocalHealthWorkoutRange`, `readLocalPreviousWorkoutRows` and `readLocalPreviousWorkout` each call `readAll()` independently. Future range projection should derive persisted legacy rows, date groups, calendar activity and per-block comparison evidence from **one verified snapshot** per load generation, preserving real `workout_logs.id`, `user_id`, `date`, `block_id`, `sort_order`, cloned sets and explicit current-catalog/historical-fallback display. Reuse G5B2A validation/identity policy; malformed/duplicate identity poisons its source instead of dropping rows. Do not pass dirty `Workout[]` drafts into persisted source evidence.

Conceptual `WorkoutRangeReadSnapshot`: `{ scope: { accountId, deviceId, namespaceKey, generationId, startDate, endDate, requestSequence, mountEpoch }, phase, result: CompositeWorkoutReadResult | null, legacyDatasetToken, sourceStatuses }`. `result.records` retain G5B2A `source/readId/localDate`, persisted legacy row or active canonical session/entry/set, capability and complete/partial/error status; a derived date index preserves distinct canonical session IDs. The token is in-memory load identity, not a new persisted field. No success is published from two different verified legacy snapshots or an old canonical generation. Legacy errors and canonical errors compose as G5B2A specifies; isolation mismatch publishes **nothing**. Keep `workout_reader` **SAFE_BY_ENCAPSULATION**, not repository-enforced read-only: only the bounded reader owns a private database handle, exposes immutable read DTOs and `close()`, and no component receives `LocalDatabaseRepository`. More direct consumers would require a stronger capability boundary.

Lifecycle owner: one Health/account scoped range-read coordinator (future implementation), not every panel adding IDB opens or focus/bootstrap listeners. Hold **one active canonical snapshot per account/device/namespace/generation/load epoch** and one paired verified legacy dataset for that epoch; derive requested date/range views from the same source snapshots, rather than rescanning on month navigation or when Previous and calendar request overlapping ranges. Key the ephemeral source snapshot by account + device + namespace + generation; key a derived range view additionally by normalized bounds. Invalidation replaces the value at the same source-scope identity. Request sequence, invalidation epoch and mount epoch are publication fences, **not persisted cache-key fields**; bound or release old range views on navigation instead of retaining an unbounded month-key collection. On A→B, A→B→A, sign-out, device change, range change, G1→G2, unmount or superseding request, close/reopen as needed and suppress late publication. Verify active generation and established device ID at publication, retry stale-generation once by reopening, as B1 does. One bounded focus/visibility recheck and `HEALTH_LOCAL_BOOTSTRAP_COMPLETE_EVENT` invalidation should belong to the coordinator; legacy save/delete should invalidate its scoped verified snapshot at commit **before** an older load can publish. Existing `AppContent` daily/static and `HealthView` month/Previous mutations remain legacy-path owners until a reviewed consumer integration; do not scatter extra callbacks. For a dormant foundation, expose an explicit `invalidate(scope)`/`retry()` contract and test it without changing the mounted writer. Avoid a persistent SWR cache at this stage: component/coordinator local state and explicit snapshot lifetime are sufficient, prevent same-scope key growth and make stale publication testable. Reconsider a shared cache only with measured cross-surface benefit and safe invalidation. One source-snapshot load budget: at most **one verified legacy `readAll()` + one canonical `listWorkoutSessions()` scan**, plus bounded metadata/generation checks; derived date/Previous/metric filters operate in memory. A focus revalidation or invalidation may repeat this bounded pair, not one pair per date/card/render/search keystroke or ordinary month navigation within the unchanged epoch.

`B1-P3-CACHEKEY`: **KEEP_NON_BLOCKING** because the dormant foundation does not touch B1's model; name and test the new ephemeral snapshot identity truthfully, but leave the existing B1 metadata field for a separate touched-file correction. `B1-P3-SAVE_DELETE_INTEGRATION_TEST`: **ACTIVATION_PREREQUISITE** (the shared invalidation semantics make the full HealthView commit-to-late-read race important); the dormant foundation can directly test its own invalidate-before-publication contract, while a later mounted integration must add the missing end-to-end test. Neither P3 is fixed by this document.

Canonical local reads stay offline and independent of Supabase success, G5A `ready`, and remote authority `OPEN`; legacy read availability is the verified local snapshot, not fabricated success after a failed bootstrap. `REL05G5A-001` malformed established device ID remains **ACTIVATION_PREREQUISITE** for broad public rollout because affected devices cannot show their canonical local records; it is not a prerequisite to implement/test the dormant range boundary and is **not fixed here**. B1's fail-closed device behavior remains. This uses the Supabase skill's auth/security principle only as a boundary check: no remote session, service key, RLS or backend authorization change is proposed.

## Rollout order, flags and activation gate

**One ordering:** (1) build/test the dormant range snapshot foundation while B1 stays default OFF; (2) independently review and wire a source-qualified Previous date-bucket view plus calendar active-day truth under preview-only child gates; (3) close Home canonical-only contradiction and source-scope or solve Search/history/PR/metric/export claims; (4) physical/local/offline QA and a separately reviewed public reader activation decision. This is a roadmap, not authorization for steps 2–4 in this PR. The first user-visible composite is still B1 selected day. Activating B1 now would put canonical-only history, Home and calendar in contradictory states. Reversibility/testing does not require production activation: static-gate tests and direct reader fixtures can exercise B1 plus the dormant foundation.

**Flag strategy:** retain `HEALTH_SELECTED_DAY_COMPOSITE_READER_ENABLED` as the parent preview gate; future mounted range/Previous/calendar consumers get a child static gate that can be true only when parent is true, with a fail-closed assertion. The dormant foundation has no product flag because it has no mounted consumer. Safe combinations: parent OFF/child OFF = existing legacy behavior; parent ON/child OFF = explicitly selected-day-only QA preview, not public; parent ON/child ON = reviewed multi-surface QA preview, still not public until Home/claim/partial QA; parent OFF/child ON = invalid and must not mount. No remote flag service, localStorage override or implicit G5A control-plane tie-in. Reader activation does not activate any writer, bind, push, pull, full resync or reset.

Minimum coherent public-reader truth set: selected-day read-only cards; Previous date-bucket history with same-day multiple sessions; Health calendar active-day union with incomplete state; Home today presence/draft distinctions; and an explicit Search scope/navigation policy that either makes canonical records discoverable through a valid read-only target or truthfully limits Search to legacy selected-day data. Per-exercise Previous/PR needs canonical comparison or a prominent legacy-only scope decision before claiming complete historical PRs. The currently unmounted metrics panel, dormant LegacyAnalytics and guarded CSV export need no implementation solely to enable a reader preview, but cannot be described as all-source coverage. Product must approve grouped order, ambiguous Previous default/selection, PR exercise comparison, mixed-source count label, Search scope/target, partial-data language and export format. A canonical-only Home “empty,” canonical-only calendar “no workout,” or unqualified complete Search/history is unacceptable for public rollout.

Physical QA must exercise Windows Edge installed PWA and iPhone Safari Home Screen Web App separately: they have separate IndexedDB/localStorage/device IDs. Test each device's own canonical and legacy records, same-day multiple canonical sessions, offline and remote-bootstrap failure, account A→B→A and generation change. Never promise unsynced canonical data appears cross-device. All seven live-writer blockers remain **OPEN**: unbound pre-reset create; rollback visibility; old/new writer coexistence; product UI identity integration; canonical field/product ownership; projection integration; reset-fenced local edit policy. Reader progress may inform identity/projection work, but closes none of these product-wide gates.
