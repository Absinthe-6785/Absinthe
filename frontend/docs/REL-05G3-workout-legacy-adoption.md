# REL-05G3: dormant workout legacy adoption foundation

G3 adds an account/project/device/generation-scoped manifest in `absinthe-local-v2` v6. It does **not** make canonical workouts the current product authority. HealthView, AppContent, the normal workout save/delete path, analytics, Vault, and the legacy backend routes remain unchanged. No startup callback invokes `runDormantWorkoutAdoption`; future orchestration must wait for Health bootstrap/recovery to settle. Remote workout push/pull and capability activation do not exist in G3.

The real clients are a Windows Edge installed app and an iOS Safari Home Screen app. Their IndexedDB stores, namespaces, device IDs, generations, and unsynced histories are independent. There is no account-global `migrated` flag. A late device can seal its own manifest after another device completed. Identical dates, block IDs, row IDs, or payloads on different devices are not automatic duplicate authority.

## Source and safety boundary

The primary source is account-scoped `workout_logs` in `absinthe.health.local` v1. `IndexedDbLocalHealthDriver.captureWorkoutAdoptionSource()` reads workout rows, referenced/current exercise blocks, and the verified import marker in one **readonly** transaction. It refuses missing/pending/inconsistent import state and never recovers, repairs, marks, deletes, or rewrites a legacy row. The captured, sorted source projection is sealed into the new canonical adoption stores before any target write. The two IndexedDB databases cannot share a transaction; the sealed copy, not a later live source read, is the adoption input. A later source change produces a new digest/manifest and never mutates a completed manifest.

The remote legacy `workout_logs` API is auxiliary only. Its POST can delete and recreate same-date/block rows; it is not a source of globally stable workout identity. Vault cloud copies and recovery imports may be stale or replace local Health state; CSV is export-only; localStorage workout drafts are unsaved work, not completed history. G3 neither adopts these as primary authority nor changes their product paths.

## Evidence and conversion

`sourceItemDigest` covers the source key, persisted row fields/sets, current block evidence, ownership, and source schema. `sourceSnapshotDigest` covers account and device-local source instance, adapter/schema, verified import marker digest, and deterministically sorted item digests. UI-derived `local_version`, iteration order, and capture time do not enter either source digest. The manifest ID also binds namespace, active generation, and conversion version 1. Source fields become immutable when sealed. Per-item evidence records classification, source projections, historical-field provenance, preallocated UUIDv4 IDs, candidate hash, target hash, and outbox mutation ID.

Current production rows have no trustworthy persisted human-session boundary. View-only session separators are never saved. Their exercise name/tags/cardio mode generally come from a mutable current catalog, not a historical snapshot. Generic recovery/import accepts additional record fields without authenticating their producer. Therefore even shape-valid `session_boundary` and `historical_exercise_snapshot` extras are **review-required**, and those historical fields are labelled `AMBIGUOUS`, not `SOURCE_EXACT`. No current production writer attests them, so the current G3 automatically adoptable range is **zero**. G3 does not combine rows by date or declare every row a standalone historical session. The dormant atomic target primitive remains for a future separately reviewed trusted producer contract; G3 does not invent one. Missing blocks or changed catalog values are retained as evidence, not replaced with UI fallback names.

Invalid numeric/set evidence is accounted separately from semantic ambiguity. G2's exact weight, repetition/assisted-repetition, duration, and kilometer helpers and `validateWorkoutSessionV1()` govern candidates. Weight source value/unit must agree with stored kg; unknown source unit is not invented. Bodyweight is not external weight zero. Set array order is preserved and canonical ordinals are one-based. Pace is derived, not canonical authority. Unrepresentable values do not silently become canonical records.

## Durability and limits

The v5→v6 schema upgrade only adds `workout_adoption_sessions` and `workout_adoption_items`; it preserves existing entities, outbox, checkpoints, conflicts, restore sessions, and migration state. Source capture and seal can be retried. Convertible items receive random session/entry/set UUIDv4 identities in the sealed item *before* a target write. `commitWorkoutAdoptionItem()` fences the active account/generation and writes the G2 `health_workout_session` envelope, existing-format idempotent outbox identity with explicit `{version:1,state:"unbound"}`, `LegacyMigrationProvenance`, and item progress in **one IndexedDB transaction**. No `requestDigest`, bound delivery, authority epoch, network send, or alternate outbox identity exists.

Final completion rechecks item counts/digests, active generation, target content/provenance/revision, and outbox identity/binding in a durable transaction. Carried-forward items retain the original target ID/hash/outbox/provenance manifest and validate the immediate predecessor and original target on first and repeated completion; `targetStateDigest` includes those dependencies. A carried unresolved review item continues to require review. `COMPLETED` can have `requiresReview=true`; every source item is accounted, not necessarily converted. Re-running the same snapshot validates all immutable seal fields and items before reusing its manifest and UUIDs. New manifests use a transaction-allocated, namespace/generation-local lineage ordinal to select the immediate predecessor, never IndexedDB enumeration order or a wall-clock timestamp. A changed source key, reappeared record, unfinished predecessor, or prior-generation adoption is review-required rather than an automatic overwrite. A completed target modified later is reported as a conflict, never silently restored by G3.

Technical persistence bounds are 5,000 workout rows, 5,000 captured exercise blocks, 256 sets per row, 128 KiB canonical UTF-8 evidence per item, 32 KiB per reference block, 4 MiB total source snapshot evidence, and 5 MiB total persisted session-plus-items evidence. These are resource limits, not workout business limits. Oversize source fails the whole capture/seal before durable adoption writes; it is never truncated or changed in Health IndexedDB. A bounded `getAll()` capture remains intentional.

G4 owns remote transport, authority epoch/CAS, receipts, inventory, and reset jobs. G5 owns product authority cutover, bootstrap sequencing, backup/restore/reset adapters, and actual Edge/iOS end-to-end validation. G6 owns deployed legacy DB evidence, rollback-proof writer fencing, old-binary behavior, and any ACTIVE transition.
